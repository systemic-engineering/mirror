### §1.3 — Five structural negatives

What @silicon IS NOT:

1. **NOT a code-generation framework in the LLVM / TVM / MLIR sense.**
   Those frameworks take a high-level IR and lower it to machine code
   via a fixed sequence of passes. @silicon does not lower — @silicon
   INFERS. The selection of which routine to emit is a @fate dice-roll
   over the existing Bauchladen of crystallized routines, restricted by
   typed cfg parameters (target architecture, compiler version, ABI).
   The Bauchladen grows; @silicon's selectivity grows with it. LLVM's
   passes are fixed at compile-time; @silicon's selection is autopoietic
   at runtime (or at substrate compile-time, which for mirror IS a form
   of runtime — the substrate-decl notation IS executable).

2. **NOT a black-box autotuner.** Autotuners (e.g. ATLAS, OpenTuner)
   search a parameter space and emit a tuned kernel. The search is
   typically blind to the structure being tuned; the tuner does not
   know it is tuning matrix multiplication, only that some kernel runs
   faster than others on the target. @silicon's @fate operator is
   typed: each round of the tournament is restricted by @algebra-
   altitude carrier types (matrix solve over field F with property P,
   eigenvalue routine for symmetric positive-definite operator, FFT
   over length-2^k complex array), by @epistemologic/reality/silicon/*
   carrier types (ISA family, SIMD extensions, cache hierarchy), and
   by γ + J + cfg restrictions (per §2.3). The dice-roll is constrained
   inference, not blind search.

3. **NOT a JIT compiler.** A JIT compiles fresh machine code at runtime
   based on observed types or hot paths. @silicon does not compile
   fresh code at the @silicon altitude — @silicon SELECTS from the
   Bauchladen of crystallized routines, where each crystal IS a pre-
   compiled (or pre-typed-and-ready-to-link) Fortran routine. The
   compilation happened at crystallization time. The selection
   happens at use time. This is closer to a content-addressed cache
   of pre-compiled algebra than to a JIT.

4. **NOT a hardware abstraction layer (HAL).** A HAL hides hardware
   differences behind a uniform interface. @silicon does the opposite:
   it EXPOSES hardware specifics via the @epistemologic/reality/
   silicon/* carriers, so @fate can dice-roll informed by the actual
   silicon. Hiding the hardware would defeat the autopoietic loop —
   the loop's whole point is to LEARN the local hardware's algebra,
   which requires SEEING the local hardware. The HAL pattern is
   substrate-pull-anti-pattern at this altitude.

5. **NOT an alternative to @io.** @silicon emits THROUGH @io.
   @silicon's emissions cross the @io boundary as concrete executable
   routines; @io/algebra IS the algebra-altitude exposure surface;
   @io/runtime-link IS the ABI-link mechanism. @silicon does not
   bypass @io; @silicon FEEDS @io with hardware-tuned routines. The
   substrate-decl above @io stays substrate-decl; @silicon's emissions
   are the bridge from substrate-decl algebra to @io-altitude
   execution.

The cycle's character at each phase:

**Phase 1** lives in @fate. The tournament dice-rolls over the existing

**Phase 3** lives in @io. The candidate crosses @io's threshold to be
actually executed. The execution measures the candidate against the
@algebra-altitude carrier's @epistemologic/property requirements

The Bauchladen has grown. The next round's Phase 1 consults the enriched

### §2.2 — What gets learned: hardware-specific algebra

The Bauchladen accumulates crystals of hardware-specific algebra. Each
crystal is one of (with examples):

**Fortran routines.** A LAPACK-style routine compiled for the host
silicon: `dgesv` (general matrix solve) compiled against Apple's
Accelerate framework on Apple Silicon, against OpenBLAS on x86_64
Linux, against MKL on Intel server. The crystal's content-address
captures (routine signature + compiled binary OID + ABI surface +
performance profile). Subsequent @fate rolls that match the routine
signature + ABI surface get a cache hit.

**SIMD patterns.** A specific use of NEON (arm64), AVX-512 (x86_64),
SVE2 (recent arm64), AMX (Apple Silicon M-series). The crystal
captures (SIMD instruction set + register layout + load/store
pattern + measured throughput on the host silicon). The next @fate
roll for a same-shape vector operation consults the crystal.

**Cache-line layouts.** A struct layout chosen to align with the
host's L1 / L2 / L3 cache geometry. The crystal captures (struct
field order + padding + alignment directive + measured miss rate
under representative workload). The next @fate roll for a same-
shape data structure on a same-cache-hierarchy host consults the
crystal.

**CPU feature exploitation.** A use of specific instructions (PMULL,
AESENC, SHA256RND) when the host's ISA flags admit them. The
crystal captures (instruction sequence + feature flag set +
measured speedup over portable fallback). The next @fate roll
under a same-feature-flag-set restriction consults the crystal.

**Memory model exploitation.** UMA-aware zero-copy host↔device
transfers on Apple Silicon, explicit-DMA staging on PCIe-attached
GPUs, NUMA-affinity-aware allocation on multi-socket servers. The
crystal captures (memory model + transfer pattern + measured
bandwidth). The next @fate roll under a same-memory-model
restriction consults the crystal.

**Numerical algorithm variants.** For a given matrix solve, the
choice between LU + iterative refinement, QR + back-substitution,
SVD + truncation depends on conditioning + size + accuracy
requirement. The crystal captures (algorithm choice + conditioning
range + size range + accuracy guarantee + measured time). The
@fate roll, given the @algebra-altitude carrier's specification of
the matrix's @epistemologic/property/* characteristics (e.g.
symmetric positive-definite, ill-conditioned, sparse), selects
the appropriate crystal.

The thread that unifies all of these: each crystal is a **typed
restriction lifted to executable form**. The substrate-decl notation
declares WHAT the algebra is (a matrix solve, an FFT, an
eigendecomposition). The @silicon altitude infers HOW the algebra
executes on the host silicon. The HOW is what crystallizes. The
WHAT stays substrate-decl-bounded.

### §2.3 — Restriction mechanisms: γ + J + cfg

The @fate tournament's dice-roll is constrained by three restriction
mechanisms. The first two come from #101 + #102 (γ + J, per the
spectral-triple-grading discipline yesterday's #103 named at agent-
coordination altitude). The third (cfg) is hardware-altitude
specific.

**γ — chirality grading.** Inherited from #101. The substrate's
spectral triple has a Z/2-grading; @silicon's emissions respect
the grading. Operationally: routines that flip the grading (e.g.
that consume a left-handed candidate and produce a right-handed
emission) are admitted only under explicit grading reversal
declared at the @silicon level. Routines that preserve the grading
are admitted freely. The grading prevents @silicon from
accidentally smuggling cross-chirality emissions into a typed
@algebra context that expects grading preservation.

**J — charge conjugation.** Inherited from #102. The substrate's
spectral triple has a real structure (J²= ±1 depending on KO-
dimension); @silicon's emissions respect J. Operationally: routines
that involve complex conjugation (e.g. Hermitian transpose,
adjoint operators) must commute appropriately with J. The
substrate-decl carrier types @algebra exposes carry J-tags; @fate's
restriction operator checks that the candidate routine's J-tag
matches.

**cfg — configuration restriction.** New at @silicon. The host's
runtime configuration restricts the candidate space. cfg is a
record:

```mirror
type cfg = {
  arch:           @epistemologic/reality/silicon/arch,
  compute_bound:  @epistemologic/reality/silicon/compute_bound,
  memory:         @epistemologic/reality/silicon/memory,
  flake_refs:     [@epistemologic/reality/silicon/flake_ref],
  abi:            @io/algebra/abi_surface,
}
```

The cfg record IS the host's identity at the silicon altitude. Two
hosts with the same cfg get the same Bauchladen behavior (modulo
empirical jitter in Phase 3 validation). Two hosts with different
cfg get different Bauchladen behavior — the same @algebra-altitude
math compiles to different @silicon/algebra crystals on a M3 Max
vs a Threadripper 7995WX.

The cfg restriction is what makes @silicon's emissions HOST-
SPECIFIC. The Bauchladen accumulates per-cfg crystals. The same
@algebra-altitude math produces different crystals on different
silicon, and the @fate tournament finds them by content-addressing
on (math signature + cfg).

Together, the three restrictions (γ + J + cfg) form the typed
restriction operator that @fate's dice-roll respects. The candidate
space is BOUNDED by the restriction. Dice-rolls outside the
restriction return ⊥ — the candidate is rejected before any
attempt at empirical validation. The bounded discipline is
preserved.

### §2.4 — The Bauchladen accumulates monotonically

Per the @bauchladen discipline (yesterday's spec at `4575340` §2): the
tray accumulates monotonically. Adding crystals never removes prior
crystals. This holds at @silicon/algebra too, but with hardware-altitude
specializations.

**Monotonic accumulation.** Every successful Phase 4 crystallization
adds a crystal. The OID identifies the crystal uniquely. Re-running
the same Phase 1 dice-roll under the same restriction → if a matching
crystal exists, cache hit; if not, fresh inference, eventual fresh
crystal. The Bauchladen grows; it never shrinks.

**Failed inferences surface @transparency<p> opacity.** Per the
@transparency property family (introduced in earlier mirror work):
when @fate's candidate generation produces a candidate that fails
Phase 3 validation, the failure does not crystallize the candidate
(non-monotonic move would be: replace prior crystal with the failed
one — forbidden). Instead, the failure crystallizes a TRANSPARENCY
REPORT: an @transparency<p> crystal whose body names (the candidate
+ the failure mode + the restriction context). Transparency reports
are themselves crystals — content-addressed, accumulated in a parallel
sub-tray. The next round's Phase 1 consults the transparency reports
to avoid retrying known-failed candidates under the same restriction.

This is the @silicon altitude's structural analogue of negative
training examples: the substrate remembers what didn't work, but
remembers it as substrate-decl-typed opacity rather than as a removed
crystal.

**Per-cfg subtree structure.** The Bauchladen at @silicon/algebra is
indexed by cfg. The path-namespace structure (per §3.1) admits
per-cfg branching. A crystal for `dgesv` on `arm64 + Accelerate +
UMA` lives at a different path-namespace location from `dgesv` on
`x86_64 + OpenBLAS + separate-PCIe`. The @fate tournament's restriction
matching selects the appropriate sub-tray automatically.

**Cross-cfg learning.** Open question §9.2: does a crystal validated
on machine A help an inference on machine B? Sometimes yes (the
algorithm choice often generalizes across cfg even when the
compiled binary doesn't). Sometimes no (the SIMD pattern that wins
on AVX-512 loses on NEON). The discipline: @silicon's Bauchladen is
host-local by default; the algorithm-choice abstraction layer can
be shared cross-host via @spectral/db distribution (per the
@spectral/db spec's distribution discipline). The crystal-level
identity stays host-local; the abstraction-level identity can
distribute.

**Monotonic growth implies bounded selectivity improvement.** Each
crystal added strictly increases the @fate tournament's selectivity
(more candidates to dice-roll over). The selectivity grows
monotonically. The substrate's epistemologic variety on axis-5
(@silicon-altitude algebra knowledge) grows monotonically. This is
the structural reason `c = r_contract × V̇ × f_lift` grows
monotonically as the @silicon Bauchladen accumulates — per
recognition #56's prediction paradigm, which IS what @silicon
implements at the hardware altitude.
